# Loom CPU and allocation investigation, 2026-10-05

The running daemon repeatedly built completion data and parsed unchanged
Markdown during streaming updates. The terminal repeatedly trimmed a growing
paragraph and scanned printable ASCII through Unicode width logic. These
were measured costs on reachable paths, rather than inferred leaks.

## Builds and observation boundaries

The daemon was PID 47391, installed from `153fc6b60` in
`~/.local/lib/loom/server.2gZwyi34`. Both terminal processes, PIDs 40075 and
5645, used `~/.local/lib/loom/client.Cwvl3kCU`, commit `553999027`.
The daemon had 16 regular schedulers; the clients had four. OTP was 29.0.5,
ERTS 17.0.5, ARM64 JIT. The installed compiler was Gleam 1.19.0; the final
comparisons used that compiler, not the default Homebrew 1.18.1.

The terminal nodes were unnamed and could not accept ordinary distributed
BEAM introspection. Native samples and isolated source fixtures were used for
them. The changed terminal Markdown module was identical between the two
installed/source revisions. The daemon accepted authenticated loopback RPC.
No running VM was restarted, hot patched or forced through garbage collection.

The machine was heavily loaded. Wall times are retained in the raw files,
but the comparison claims below use reductions and allocated words. Allocated
words measure cumulative work; they are neither retained heap nor OS RSS.

## Live evidence

Two ten-second reduction cuts showed workload variation. In the first, the
SQLite worker consumed 10.48 million of 24.66 million reductions and the
operator page 7.18 million. In the next, the page consumed 35.13 million of
48.39 million reductions (72.6%). Empty mailboxes at the observation instant
are not evidence that no backlog ever formed.

A three-second `tprof` call-time cut of six selected actors attributed
1.044 seconds of 1.226 seconds of measured function time to the operator
page (85.2% within that selection). It handled 110 updates and built 110
views: 108 streaming batches, one tick and one session-list response.
`completion.table` ran 110 times; command filtering ran 109,120 times.
Markdown parsing ran 220 times. The component's projection rebuilt once,
so the already installed projection cache was working. This was render work
on stream arrival, not an idle timer storm.

A separate three-second call-memory cut allocated 45.09 million words
across the selected actors. The page accounted for 27.83 million words
(about 212 MiB of cumulative allocation). A SQLite burst accounted for
14.86 million words. These cuts are different workload moments and cannot
be added together or interpreted as resident growth.

Pickglass provided independent evidence:

- Its five-second sampled profile collected 3,000 process samples at about
  99 Hz. Of those, 118 were running/runnable and 2,882 waiting. SQLite fetch
  appeared in 23 of the 118 samples. Sample shares are not elapsed CPU shares;
  sampling undercounts work inside BIFs/NIFs and limits stack depth.
- Its exact `web_view*` call trace reached the 100,000-event budget after
  1,417 ms, before the requested three seconds. Within that bounded trace,
  completion-table construction occupied 38.8% inclusive time and settled
  report rendering 27.7% inclusive, 18.8% exclusive. Trace times include
  descheduling and charge untraced callees to their traced caller.
- The capture held 3,406 records plus header/footer. At its observation cut,
  VM memory was 193.9 MiB, process memory 133.7 MiB, binaries 16.4 MiB,
  code 23.6 MiB and ETS 1.7 MiB. The 200 captured processes summed to
  129.7 MiB of allocated process memory. This is not a full reachability census.

The earlier full census held 369 processes and 228.3 MiB total VM memory,
including 165.1 MiB process memory and 20.3 MiB binaries. Allocator carriers
were 285.8 MiB against 216.9 MiB allocated in the scanned allocators. Native
physical footprint was 257.3 MiB for the daemon and 71.3 MiB for the hotter
terminal. Later cuts varied with activity; none ran the candidate. The native
terminal stack sample showed substantially more GC/copy activity than the
daemon sample, but JIT stack opacity prevented attributing it to a function.

A later payload-free state walk found three static supervisors at about
5 MiB each. Their largest restart-argument path led through
`client@serve:assemble_in` to a 28-entry tool registry, about 1.84 MiB in
expanded term-copy words. The supervisor's whole returned state expanded to
about 11.8 MiB. `sys:get_state` copies the state before inspection and can
lose sharing; even its unique-word count describes that returned copy, not
exclusive words on the original heap. This names a retention path but does
not establish a leak or removable ownership. The original operator-page PID
had exited by this later cut. Before changing restart custody, inspect which
registry callbacks capture avoidable configuration and measure the proposed
copy boundary. The raw type-only walk is `retention-shapes-path.txt`.

All profilers stopped, Pickglass released its pins and unloaded its injected
modules. The final RPC check reported no `tprof` controller and only the
legacy default trace session. A separate profiler admission conflict was
resolved by releasing the existing viewer, not by bypassing admission.

## Changes and invariants

The web editor projects the returned prompts before constructing its memo
closure. Completion-table construction runs only when those prompts change.
The recent-answer preview projects its answer and recent chip; unrelated
model updates do not parse that Markdown again. Settled result reports reuse
their whole element fragment until the report changes.

These are leaf memos. Lustre 5.7.1 discards nested memo entries when an outer
memo hits, so a report uses direct parsed Markdown inside its own memo rather
than nesting the existing card-body memo. Rendered content, total decoding,
wire types and public interfaces are unchanged. Tests carry Lustre's real
cache through successive renders, count constructor calls with private OTP
trace sessions, and check patches when the inputs change. All three new
regressions fail against the installed baseline modules on the unwanted
constructor call (one call rather than zero), and pass against the candidate.

The terminal's soft-break join no longer trims its accumulated head. Both
callers supply a parser-created paragraph whose head is already trimmed.
A checkpoint test compares every incremental frame with a full render,
including trailing spaces and Unicode. The change removes repeated copying
without weakening hard-break or styling behavior.

Etui keeps the original Unicode implementation as a fallback for the whole
string. Its fast width pass accepts only bytes 32 through 126. Any control
or non-ASCII byte rejects the fast pass, so an ASCII base followed by a
combining mark or VS16 still reaches the original grapheme logic. Single
ASCII graphemes avoid Unicode property scans. Left-aligned rows no longer
measure their complete width just to compute a zero offset; right and center
alignment still do. No new dependencies or public API were introduced.

## Matched local comparison

Each case ran in a fresh single-scheduler VM. Baseline and candidate were
alternated twice with Gleam 1.19.0. The web comparison replaced only the
three changed web modules with their installed baseline BEAMs; the terminal
comparison replaced its changed Markdown module and, for the combined
candidate, loaded the two changed etui modules. Common dependencies and
fixture inputs were held constant.

| Workload | Baseline | Candidate | Reduction |
|---|---:|---:|---:|
| 100 unchanged operator views, reductions | 2,717,863 | 454,369 | 83.3% |
| Same views, allocated words | 3,544,961 | 752,619 | 78.8% |
| Stream at 2,048 frames, reductions/frame | 9,622.9 | 3,604.0 | 62.5% |
| Same stream, allocated words/frame | 22,322.3 | 10,502.5 | 53.0% |

The reductions and word results repeated across both runs. The stream is one
long paragraph, a newline every twelve words, drained in 64-frame ticks.
The terminal candidate includes both the Loom paragraph change and etui's
width/alignment changes. The candidate is not installed in the live processes.

The six-agent 120-by-40 render/scroll witness matched byte for byte: 4,800
styled cells and cursor state, 249 transcript rows, scroll offset 60, and
40 wheel frames. Both files hashed to
`B60D8A797237CF55B6D043601D2EFA6A7A48AC5DF639CD2CA03DDF1C0575CD8A`.
That fixture also reduced median paint reductions from 321,587 to 184,396.
It does not establish that every live terminal workload falls by that amount.

## Remaining measurement

The measured wins remove avoidable allocation and CPU work. They do not
prove an installed resident-memory improvement or resolve issue #454.
After selecting and restarting an approved candidate, repeat matched live
streaming, settled-report and terminal scroll workloads. Keep scheduler work,
process heaps, allocator carriers and physical footprint separate. Observe
post-workload residency without forcing GC before making a retention claim.
SQLite activity remains workload-dependent and was not changed by this work.
