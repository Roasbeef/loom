# Trace-driven optimization: how the harness proposes its own changes

Status: **note, not a work package.** Nothing here is built. It answers a
question the milestone's name raises and `docs/next.md` item 4 leaves
open: with the tier-H loader deferred, what does *self-extending* mean,
and how would the harness ever decide to extend itself? The answer this
note argues for is that the harness never decides. It reads its own
execution traces, proposes candidates onto the promotion ladder that
already exists, proves them against live rollouts, and waits for a
recorded decision. The issue tracks the work; the code is the truth
where the two disagree later.

## The ask, restated

Given a trace of agent execution, could the harness use it to optimize
itself? Concretely: could it spawn a sub-agent with the trace and the
relevant system code and have it produce a change, up to and including
a hot-loaded `.beam`? And in a more advanced form, could it run a
GEPA-style search (Agrawal et al., 2025, *GEPA: Reflective Prompt
Evolution Can Outperform Reinforcement Learning*, arXiv:2507.19457) so
that when a new model is released the harness learns, from that model's
own traces, which tool shapes and instructions it works best with?

Yes to nearly all of it, with one substitution. The output of the
optimizer is never a `.beam` and never a body resident in the harness
VM. It is a candidate on the ladder design §7 already draws, and the
component it most often mutates is text the tree already parametrizes.

## What the tree already decides

Five rulings stand and this note does not reopen them.

- **Rule Zero and the frozen TCB** (`docs/loom-design.md` §7 hard
  rules). Model-influenced code never runs in the harness VM. Storage,
  the state machine, the broker and the sandbox drivers do not change at
  runtime. Self-improvement grows the tool and hook surface only.
- **Nothing self-promotes.** The agent proposes; a promotion is a human
  decision or a pre-declared signed policy, recorded durably. An
  optimizer is an agent, and this rule binds it exactly as it binds a
  strand a person is talking to.
- **The tier-H loader is deferred** (#32, decided 2026-09-03). A survey
  of about 490 pi extensions found none that needs code loaded into the
  harness VM; every hook is expressible in the jail. An optimizer that
  needs tier H to land its output would be the first resident consumer,
  and this note argues it does not need one.
- **Text a model can write is prompt injection with a delivery
  mechanism.** `client/rules.gleam` refuses model-writable rules on this
  ground and `docs/architecture/memory.md` keeps the memory store out of
  the workspace for the same reason. A candidate the optimizer proposes
  is therefore never applied by the optimizer; it is *proposed*, and the
  posture of the component it targets says who applies it.
- **The system prompt is pinned per session.** `client/system_prompt`
  renders the pack once at session open and pins the bytes, because the
  rendered string sits behind a prompt-cache breakpoint and its economics
  rest on the head not moving. A prompt change lands at the *next*
  session open. This is why "hot" is the wrong axis for most of what the
  optimizer will touch: the change is versioned and takes effect on the
  next boot, and rollback is pointing at the previous version.

One line in the tree is worth quoting because it is the whole note in
miniature. `packages/prompt/src/prompt/pack.gleam` opens: *"The system
prompt is text that will be optimized — mutated, scored, and replaced —
without a release. So the words live in a pack ... mutate the pack, run
the evaluation, keep the winner, and never touch Gleam."* The pack was
built as an optimization target. Nothing yet does the mutating, the
scoring or the keeping. This note is the design for those three verbs.

## Decision 1: the trace is the session file

No new tracer is built. The write-once conversation tree already
records, per strand, everything an optimizer needs to reflect on:

- every assistant turn as a `MessageEntry`, whose `AgentMessage` carries
  the provider, model id and API it was generated by, so a trace is
  attributable to a model without any side table;
- every tool call and tool result as content of those messages,
  including the broker's in-band structured refusals, which is where "the
  model kept trying something the jail refuses" is visible;
- every compaction as a `CompactionEntry` with `tokens_before`, which is
  where "this model overflows context on this kind of task" is visible;
- every cost as a `UsageRow` in the ledger, the billing source of truth,
  with tokens and cache reads per turn;
- anything a hook or a tool wanted remembered as a `CustomEntry` under a
  registered type.

There is also already a consumer that reads settled sessions after the
fact and writes derived rows with provenance: the distill pass
(`client/distill.gleam`, `client/distillpass.gleam`) walks the session
directory and produces `memory/fact`, `memory/lesson` and
`memory/preference` rows into `loom-memory.db`, a session file kept
beside the repository's sessions. Design §8 says promoting a lesson to an
L1 skill is one step. The optimizer is a *second producer* of the same
kind: same input, same walk, same provenance discipline, a different
registered output type in its own session file.

Two things the trace does not carry today, and needs to:

- **An outcome.** Nothing records whether the task the run was asked to
  do was accomplished. `agent_end` is fired before the terminal
  transaction commits and deliberately carries no outcome word, and
  `agent_settled` has no producer. Without an outcome the only fitness
  signal is cost, and an optimizer that minimizes cost alone learns to do
  less. The first piece of work is a durable outcome row: an evaluator's
  verdict for a scripted task, or a person's mark for a live session,
  written as a `CustomEntry` the optimizer can join to the usage rows.
- **Redaction.** `telemetry` scrubs secret-shaped values before a line is
  written; the conversation store does not, because it is the record and
  must be faithful. A trace excerpt handed to an optimizer sub-agent
  therefore passes through the same `telemetry/field.scrub_text` rules
  (and the workspace path rules the memory store applies) on the way into
  the brief. The store is never scrubbed; the brief always is.

## Decision 2: the output is a candidate on the ladder, never a resident body

The optimizer produces one of the following, and nothing else. Each row
names the rung, who applies it, and how it is undone.

| Component | Rung | Applied by | Undone by |
|---|---|---|---|
| The system prompt pack | text, L0 cost | a new pack version, selected for the next session open | pointing at the previous version |
| A tool description, including the `code_mode` prelude description | text, L0 cost | a description overlay, versioned like the pack | dropping the overlay |
| A triggered rule (`[[rule]]`) | operator config | the operator edits `loom.toml`; restart is the trust decision | deleting the rule |
| A code-mode program worth keeping | L1 skill (#30) | saved as source, re-vetted and recompiled on every invoke | deleting the entry |
| A tool or hook | tier-J extension | a manifest and source through the ordinary install path and its record | `loom ext` uninstall |
| An adapter or harness defect | L4 | a pull request to Loom | a revert |

The `.beam` is not in the table, and the reason is not caution. Design
§7's rule that we never load a `.beam` we did not compile is about
provenance; Rule Zero is about *authorship*, and it is the one that
bites. Even a body the harness compiled itself from vetted source is
model-influenced code, and the only place a resident body is worth
having is a place a jailed body cannot reach: synchronous access to
harness state. That is the TCB. So the two rulings compose into: a
change to how the harness itself behaves is L4, a pull request a person
reviews, and everything an optimizer may land at runtime is a change to
what the model reads, what it may call, or what runs in the jail.

The "newly released model" case makes the point concretely. What
differs between models is which tool shapes they reach for, how much
instruction they need before a `code_mode` program beats six tool calls,
how they react to a refusal, and how soon they overflow. Every one of
those is a fact about the pack, the tool descriptions and the rules.
The one class that is not, an adapter quirk such as the Gemini
thought-signature replay defect found by driving the dialect live, is
code in the provider package, is found by exactly the kind of review a
trace-fed sub-agent could run, and is fixed by a pull request.

The second row does not exist yet. Tool descriptions are constants in
`packages/tools`, and the `code_mode` description is generated from
`packages/cap` and gated by `make prelude-check`. A per-model description
overlay is a small seam and is the one piece of new mechanism Decision 2
asks for; the pack already has its versioning and its selection story.

## Decision 3: the optimizer is a jailed sub-agent run as a batch job

The optimizer is a strand like any other: it has a scoped context in and
structured results out, its full transcript stays in its own session
tree for audit, and it holds no capability the pack it is mutating could
not name. It runs as a batch job the operator starts, or a scheduled
heartbeat fires, never inside the drive loop of a session doing real
work. This is the same lifecycle shape as the distill pass, and it
should be the same `weft/state_machine` skeleton: begin, run under a
wall deadline, settle, and refuse rather than overlap.

Its brief is assembled by the harness, not by the optimizer:

1. the component under test, verbatim, with its version;
2. redacted excerpts from the source sessions, selected by the harness
   for the model id under study and for the signal being chased (the
   refused calls, the overflowing turns, the tasks with a failing
   outcome);
3. the scores of the current component and of every prior candidate for
   this model, so the reflection is on a history rather than a snapshot.

Its output is a `CustomEntry` under a reserved type, say
`optimizer/candidate`, in a session file kept beside `loom-memory.db`
and under the same rule that a model never writes to the workspace:
the candidate text, the component and version it derives from, the
source session and entry ids it reflected on, and the model id it is
for. Provenance is not optional here; a candidate with no source entries
is refused by the decoder, because a promotion decision is made against
evidence and the evidence is the trace.

GEPA maps onto this without translation. Its loop is: sample a task
batch, run the current program, hand the *execution traces* and the
scores to a reflective model that proposes a mutation to one text
component, evaluate the child, and keep a Pareto front across tasks
rather than a single best. The trace is the session file. The text
component is the pack or an overlay. The reflective model is the
optimizer sub-agent. The front is a set of candidate rows and their
score rows. Keying the front by model id is what turns "optimize the
harness" into "learn this model's profile", and it costs nothing
because the id is already on every turn.

The optimizer's own pack is never a candidate. A loop that mutates the
instructions of the process doing the mutating has no fixed point a
person can reason about, and the whole design rests on there being one.

## Decision 4: evaluation is live rollouts, and the outcome comes first

A candidate is scored by applying it as a per-session override and
running a fixed task set against the live model, as a fan-out of
subagents through the orchestration seam that already exists. Nothing
else measures model behaviour. In particular the deterministic
simulation runner (`docs/architecture/simulation.md`) is *not* the
evaluator: it scripts the provider so that the same script converges
under every fault schedule, which proves a harness change is safe and
proves nothing about what a model does when it reads different words.
The runner keeps its job, which is to gate any code this work adds.

The score is a vector, and its first component is the outcome row from
Decision 1. Then, from the ledger and the tree: tokens and cost per
settled task, turns to settle, refusals, tool-call errors, compactions.
A candidate that improves cost and worsens outcome is dominated, not
improved; the front is Pareto and the operator is shown the front, not
a scalar. This is the specific defence against the failure GEPA's
authors and everyone who has optimized against a proxy have seen:
optimize the ledger and you will be handed a prompt that does less.

Rollouts cost real money and real minutes. A GEPA-style search wants
tens of rollouts per candidate and tens of candidates, so the job
carries a budget in the usage ledger's own units and stops when it is
spent, the same pooled budget discipline `code_mode` executions already
have. The task set is fixed and versioned alongside the candidates, so a
front is comparable across runs and so that overfitting to it is at
least visible: a candidate that wins on the set and loses on the next
week's live sessions is a fact the outcome rows will record.

## Decision 5: promotion is a recorded decision, and rollback is a version

Applying a candidate is the operator's act or a signed policy's, written
durably as the install record for an extension is written today: which
candidate, which evidence rows, who or what approved, when. The applied
version is what the next session open reads; the previous version stays
addressable; rollback is selecting it, and is itself a recorded
decision. For the pack this needs no new mechanism beyond the selection
record. For descriptions it is the overlay seam. For rules it is an
editor and a restart, which is already the posture. For skills and
extensions it is the ladder as designed.

This also pays a debt. The plan's M6 closing criterion still owes an
L0→L3 ladder test with a live rollback, which cannot exist without a
loader. A rollback of an applied pack or overlay version, proven by a
session opening under the previous bytes, is the same claim made about
the thing that actually changes at runtime here, and it can be built
and tested now.

## What this is not

- **Not tier H.** Nothing here reopens #32. If a resident consumer ever
  appears, it appears on its own merits and through that issue.
- **Not automatic.** The loop proposes and evaluates without a person;
  it applies nothing without one, or without a policy a person signed.
- **Not weight training.** GEPA is chosen precisely because it optimizes
  text with a handful of rollouts and a reflective model, which is the
  budget a per-user harness has. Nothing here touches a model.
- **Not a second memory system.** Lessons about the *workspace* stay in
  `loom-memory.db`. Candidates are about the *harness's own words and
  surface*, are keyed by model, and live in their own file. The two
  producers share a walk and a discipline, not a store.

## Phases

1. **The outcome row and the redacted brief.** A durable outcome
   `CustomEntry` with a producer for scripted tasks and a TUI mark for
   live ones; a trace-excerpt selector over a session directory keyed by
   model id and signal; the scrub pass into the brief. Exit: a brief for a
   named model, built from real sessions, contains no secret-shaped value
   and joins each excerpt to its usage and outcome rows.
2. **One pack candidate, end to end.** The optimizer strand, the
   candidate type, a fixed task set, the rollout fan-out with a budget,
   the score rows, the selection record, and rollback. Exit, and the
   acceptance test for the note: from recorded sessions on one model the
   pipeline proposes a pack candidate, evaluates it beside the baseline
   over the task set, records the front, an operator approves it, the
   next session opens under its bytes, and a rollback opens the one after
   under the previous bytes, with every step a row.
3. **Descriptions and rules.** The per-model description overlay seam,
   and rule candidates surfaced to the operator as proposed `[[rule]]`
   text rather than applied.
4. **Skills.** Once #30 exists, a program the traces show being
   rewritten repeatedly becomes an L1 candidate through the same path,
   with #31's test-in-jail as its evaluator.
5. **The search.** Pareto front over the task set, multiple candidates
   per generation, per-model profiles kept across releases. Phase 2's
   single-candidate loop is the unit this generalises, and it must be
   boring before the search is worth its budget.

## Open questions

- **Who marks a live session's outcome?** A scripted task has an
  evaluator; a live session has a person, and a mark they never give is
  a missing row, not a failure. Whether an absent mark is excluded or
  scored as neutral changes what the front rewards.
- **How wide is a task set?** Too narrow and the candidate overfits;
  too wide and a generation costs more than a week of real use. The
  answer is probably per repository, and probably starts at ten.
- **Does a candidate carry a model id or a model family?** A profile
  per exact id is the honest unit and never shares a wrong lesson; a
  profile per family reuses one across point releases. Start per id.
- **Where does the overlay seam live?** The tool registry is the obvious
  owner, but the `code_mode` description is generated and gated, and an
  overlay over a generated artifact needs the gate to know about it.
