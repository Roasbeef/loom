# ADR-019: Khepri holds session ownership, and its members are the orchestrators and the executors

**Status**: proposed · **Date**: 2026-10-08 · **Supersedes**: the phase 5 ruling
that two catalogue rows are the move authority (protocol-change/078, the
addendum on moving a session) · **Spec ref**: protocol-change/079 ·
**Issue**: #697

## The question

Phase 3 of the distributed runtime made the session directory an interface,
`client/session_directory.Directory`, backed by a two-second parallel lookup
over the other orchestrators' catalogues. Phase 5 made a move's authority two
catalogue rows on two machines, the source's `moving` and `moved` and the
receiver's `imported`, ordered by a write-ahead intent. Both phases kept each
catalogue as the source of truth for the sessions it holds.

The owner has decided that the next step toward failover is a single
authoritative record of which orchestrator owns each session, kept by Khepri,
and that a move is a compare-and-set on that record instead of the two rows.
The owner has also decided that the cluster's voting members are the
orchestrators and the executors, so a deployment of two orchestrators and one
executor still has a majority when one machine is down. Automatic failover is
not part of this decision.

That leaves five questions, and this record answers them:

1. Which replicated store, and why not something we write ourselves?
2. Which versions, and do they work with this repository's toolchain (Gleam
   1.19, OTP 29)?
3. How does an Erlang dependency enter a Gleam package here, and where does
   the code that calls it live?
4. Can the store run over Loom's distribution as it is configured today
   (pinned TLS, hidden nodes, `dist_auto_connect` set to `never`)?
5. What does it cost?

[`docs/architecture/directory.md`](../architecture/directory.md) describes the
design that follows from these answers, and
[protocol-change/079](../../protocol-change/079-khepri-session-ownership.md)
specifies the interface changes.

## Measured before deciding

Every claim in this section was produced by a throwaway spike under the
worktree's `build/` directory, which is ignored by git and was not committed.
The commands and the raw numbers are in the appendix.

**The dependency builds as an ordinary Hex dependency of a Gleam package.**
Adding `khepri = "== 0.19.3"` to a fresh Gleam 1.19 project's `gleam.toml`
pulled six Hex packages (khepri 0.19.3, ra 3.2.0, horus 0.5.1, aten 0.6.0,
gen_batch_server 0.10.0, seshat 1.0.1) and compiled them with rebar3 3.27 on
OTP 29 (ERTS 17.0.5). The compile prints ten Erlang warnings, all
`'catch ...' is deprecated`, from the dependencies. `gleam build
--warnings-as-errors` exits 0, because that flag governs Gleam's own
warnings and not those of a rebar3 dependency. The repository already
depends on rebar3 packages the same way (`esqlite_loom`, `yamerl`, `cowlib`).

**A store works in a VM without distribution.** `khepri:start(Dir, #{cluster_name
=> loom_dir})` on `nonode@nohost` starts a one-member store, so the unit tests
of the code that calls Khepri can run in the ordinary test VM. A
compare-and-swap there takes 0.29 ms at the median and 1.4 ms at p99 over 300
sequential writes.

**A three-member cluster forms over Loom's TLS distribution.** Three member
emulators and one controller emulator were each booted with `-proto_dist
inet_tls -ssl_dist_optfile <file>`, where every options file was generated by
the repository's own `client_distribution_ffi:options/2` and every member was
started by the repository's own `client_distribution_ffi:start/4`. Every node
pinned the leaf certificate of every other node. Each member started a store
on its own data directory, and two of them joined the third with
`khepri_cluster:join/3` (4 to 210 ms). Creates, compare-and-swaps and a
transaction with an anonymous function (which exercises horus) all behaved as
documented on OTP 29.

**Ra does not work over hidden connections.** With the nodes hidden, as
`client/distribution.start` makes them today, the cluster formed and accepted
writes, but three things failed:

- A member that was down while the leader wrote past a snapshot never caught up
  after it came back. Its log stayed at index 10 while the leader was at 5012,
  for the whole 20 s the test waited. Ra's leader sends a snapshot only to a
  node in `nodes()` (`ra_server_proc`, the `send_snapshot` effect), and
  `nodes()` lists visible connections only.
- After two of three members stopped, the survivor still reported itself as
  leader. Ra and its failure detector, aten, learn about peers from
  `net_kernel:monitor_nodes/2` without `{node_type, all}` and from heartbeats
  sent only to `nodes()`, so with hidden connections they receive neither.
- A member restarted after quorum loss did not reconnect on its own. Ra dials a
  peer it does not see in `nodes()` when its server starts, and over hidden
  distribution that dial did not produce a connection, so quorum did not
  return until something else connected the nodes.

**Ra works over visible connections with automatic connection still off.** The
same run with the members started with `hidden => false`, booted with `-kernel
connect_all false`, and with `dist_auto_connect` still `never` and the same
`net_kernel:allow/1` list passed all three checks. The restarted member caught up
through a snapshot in 409 ms. A restarted member's Ra server dialed its peer
itself, quorum returned, and the next write committed in 11 ms. `nodes()` on each
member listed exactly the pinned nodes that had been connected and nothing
else.

**Latency on one host.** Over loopback TLS, a compare-and-swap issued on the
leader took 1.0 to 1.2 ms at the median and 3 to 6 ms at p99, and one issued on a
follower took 0.7 to 0.9 ms at the median. A local read (`favor =>
low_latency`) took 2 µs at the median on any member. A read with `favor =>
consistency` took 2 to 4 µs on the leader and 70 to 90 µs on a follower. After
the leader was stopped, the first write on a survivor succeeded 200 to 700 ms
later.

**Without a majority, writes time out and local reads keep working.** With one
member of three running, a write with `timeout => 3000` returned `{error,
timeout}` after 3.0 s. A local read returned the last value the member had
applied in 0.2 ms. A read with `favor => consistency` and `timeout => 3000` did
not return within 60 s, when the controller's call to it gave up: that path does
not honour its timeout.

## Decision

**Khepri 0.19.3 over Ra 3.2.0, pinned exactly.** `packages/client/gleam.toml`
gains `khepri = "== 0.19.3"`. Khepri's own Hex requirements pin Ra, horus and
their dependencies to exact versions, and `manifest.toml` records them, so one
line pins the whole set. An upgrade is a deliberate change with its own gate
run, because Khepri is below 1.0 and its API has moved between minor
versions.

**Why Khepri and not something written here.**

- *A Raft of our own* would put consensus, log compaction, snapshot transfer,
  membership change and failure detection on Loom's maintenance list. Ra is
  the Raft implementation RabbitMQ runs its quorum queues and its metadata store
  on, and Khepri is that metadata store. The property we need, one linearizable
  compare-and-set register per session, is a few lines of Khepri.
- *SQLite with a designated authority node* is what phase 5 avoided by keeping
  the authority on the two catalogues, and it reintroduces a single node whose
  loss stops every move and every creation. Replicating SQLite (with a tool
  such as LiteFS or rqlite) adds a process outside the BEAM and a second
  network protocol beside distribution.
- *Ra without Khepri* gives the log and the state machine but not the tree, the
  conditions, the fence, or the joining and resetting of members, all of which
  we would write against Ra's API instead.
- *The two catalogue rows* (phase 5) stay correct for a move, but they cannot
  express failover: a takeover needs a record that a third orchestrator can
  read and change when the owner is gone, and the two rows live only on the two
  machines involved.

**The cluster's members talk over visible distribution connections.** This is
the one change to the distribution posture, and the spike made it necessary
rather than chosen. A daemon that is a directory member starts distribution
with `hidden => false`. Its boot arguments add `-kernel connect_all false`, so
`global` never connects to a node because a peer knows it, and `-kernel
prevent_overlapping_partitions false`, so `global` never disconnects one member
from another because a third lost sight of it. `dist_auto_connect` stays
`never`, the pins and the `net_kernel:allow/1` list are unchanged, and a daemon
that is not a member stays hidden. The spike measured `connect_all false` but did
not set `prevent_overlapping_partitions`; the first implementation slice
measures it before the flag is relied on. The cost is listed below.

**The Erlang dependency is reached through one FFI module.** Khepri's functions
return Erlang shapes (`ok`, `{ok, Value}`, `{error, Reason}` with nested
records) and raise on some misuse, so `client/internal/ffi_khepri.gleam`
declares the externals and binds them to one shim, `client_khepri_ffi.erl`,
which normalizes every return to a Gleam `Result`, catches exceptions at the
boundary, and builds no atom from input (the store name and the path roots
are literals). The module's doc comment says why no pure alternative exists:
`gleam_stdlib`, `gleam_erlang`, `gleam_otp` and weft have no replicated store.
Every value read back from the store crosses a total decoder, because Ra's log
and snapshots are durable storage. Every call that can wait on a quorum runs in
a weft task under a deadline, because Khepri's consistent reads do not honour
their own timeout (measured above).

**The package is `client`.** The directory interface, the mover and the
importer already live there, and the only package downstream of `client` is
`conformance`. `core`, `machine`, `prompt` and `session_view` are untouched,
so lint R6 is unaffected.

## What was considered and refused

- **Keeping the nodes hidden and working around Ra.** The snapshot path, the
  node monitor and aten's heartbeat all read `nodes()`. A fork of Ra that reads
  `nodes(connected)` would work and would put a patched consensus library on
  our maintenance list; the repository already carries forks (mist, gramps)
  where it had no choice, and here it has one.
- **Executors as non-voting members.** Ra supports non-voters, and they would
  keep the store off machines that hold checkouts. The owner ruled the other
  way, because two orchestrators alone have no majority once either is down.
- **Recording only sessions on an executor.** A local session can never move,
  so its ownership never changes. Leaving it out of the store would keep the
  phase 3 fan-out alive for it, and two lookup mechanisms are more to maintain
  than one record per session. Protocol-change/079 records local sessions and
  lets them open without a quorum.
- **Automatic bootstrap of the cluster by the first configured member.** A
  member that loses its disk and is first in the list would start a second,
  empty cluster. Bootstrap is an explicit operator command run once
  (protocol-change/079).

## What it costs

- **Six new Hex packages and roughly 2 MB of BEAM files** (Ra 1.1 MB, Khepri
  640 KB, the other four 236 KB), plus the OTP applications `sasl`, `compiler`
  and `tools` that horus and Ra require at runtime, which the release's relx
  closure picks up. `packages/client/manifest.toml` and
  `packages/conformance/manifest.toml` both change, and the second must be
  updated by hand in the same commit, because CI's Gleam does not heal a
  downstream manifest.
- **A quorum for the writes that change ownership.** Creating a session,
  opening a session on an executor, beginning, finishing or abandoning a move,
  and deleting a session each need a majority of members. Lookups, archive,
  restore, local sessions and every running session do not.
- **Visible distribution between members.** `nodes()` lists the other members.
  `pg` scopes with the same name on two members exchange their membership;
  Loom's event bus publishes to local members only, so delivery does not change,
  but membership traffic does cross the connection. `global`'s name table and
  locks span the members; Loom registers no global names, and Khepri takes a
  global lock while a member joins.
- **Ra dials its peers.** A Ra server connects to the members it does not see
  when it starts, which is a connection made by a library rather than by
  `client/distribution.connect`. It can only reach nodes on the
  `net_kernel:allow/1` list, all of which are pinned.
- **Executors pin each other** when more than one is a member, because any
  member can become the leader and the leader must reach every follower.
- **Disk and memory on every member**: a Ra write-ahead log, segments and
  snapshots under the daemon's state root, and the whole tree in memory. One
  record per session is a few hundred bytes.
- **A pre-1.0 library.** Khepri's API has changed between minor versions. Because
  of the exact pin, an upgrade happens only on purpose, and because every call goes
  through one FFI module, an upgrade's code changes stay in that module and its
  shim.

## Appendix: the spike

The spike was a Gleam project at `<worktree>/build/khepri_spike` with three
source files: a copy of `packages/client/src/client_distribution_ffi.erl`, an
Erlang driver `kspike.erl`, and the generated Gleam module. The driver minted a
CA and one certificate per node with `public_key:pkix_test_data/1` (the same
calls as `test/client_distribution_fixture_ffi.erl`), wrote each node's options
file with `client_distribution_ffi:options/2`, and launched the controller as a
fourth pinned TLS node. The controller spawned each member through
`open_port/2`, so a member exited with its port, and drove every step with
`erpc`. The variant `hidden` started members with
`client_distribution_ffi:start/4`; the variant `visible` started them with the
same settings and `hidden => false`, and added `-kernel connect_all false`.

Commands, run from the worktree with absolute paths:

```sh
gleam new --skip-git --skip-github <worktree>/build/khepri_spike
env -C <worktree>/build/khepri_spike gleam build                 # deps and compile
env -C <worktree>/build/khepri_spike gleam build --warnings-as-errors   # exit 0
<worktree>/build/khepri_spike/run.sh hidden    # three members, hidden nodes
<worktree>/build/khepri_spike/run.sh visible   # three members, visible nodes
```

`run.sh` ran `kspike:main/1` in a plain VM to provision, then the controller with
`HOME` set to its own directory and the TLS flags, which ran
`kspike:control/1`. The machine was an Apple Silicon Mac on macOS 15.5. The
emulators registered with the epmd that was already running and deregistered
when they exited; no emulator or epmd started by the spike was left running.

| Step | Hidden | Visible |
|---|---|---|
| `khepri:start/2` per member | 105 to 131 ms | 57 to 86 ms |
| Two `khepri_cluster:join/3` | ok, 11 and 210 ms | ok, 4 and 5 ms |
| `create` twice on one path | ok, then `{error, {khepri, mismatching_node, _}}` | same |
| CAS with a stale expected value | `{error, {khepri, mismatching_node, _}}` | same |
| Transaction with a fun (horus) | ok | ok |
| CAS on the leader, 300 sequential | p50 1.2 ms, p99 3.3 ms | p50 1.0 ms, p99 6.0 ms |
| CAS on a follower, 300 sequential | p50 0.9 ms, p99 4.2 ms | p50 0.7 ms, p99 3.6 ms |
| Local read, 2000 | p50 2 µs | p50 2 µs |
| Consistent read on a follower, 2000 | p50 70 µs, p99 202 µs | p50 88 µs, p99 429 µs |
| A write on a follower after 8 s idle | ok, 7 ms | ok, 6 ms |
| Member down for 5000 writes past a snapshot, then restarted | never caught up (index 10 of 5012 after 20 s) | caught up in 409 ms through the snapshot |
| First write after the leader stopped | ok after 202 to 706 ms | ok after 404 ms |
| Write with one member of three | `{error, timeout}` after 3.0 s | same |
| Local read with one member of three | last applied value in 0.2 ms | same |
| Consistent read with one member of three, `timeout => 3000` | no answer in 60 s | same |
| Leader query with one member of three | stale leader reported | timeout |
| A stopped member restarted with no explicit connection | no connection; next write timed out after 10 s | Ra dialed its peer; next write ok in 11 ms |

To force snapshots in the catch-up row, the stores were started with the machine
configuration `unreleased_command_footprint_threshold => 65536` and
`snapshot_time_interval => 0`. With Khepri's defaults, 5000 small writes took no
snapshot at all, because Khepri requests one only after 20 MiB of unreleased
commands.
